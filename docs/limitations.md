# Limitations of the gate

The gate (`gate/`) is a Claude Code Stop hook: when a turn changed code, it runs the project's tests and does not let the agent finish while they fail or did not really run. The mutation command (`gate/mutate.js`, the plugin command `/greenwashing:mutants`) breaks the changed code and runs the tests after each break. These are their known limits in v0.1. Each one follows from a design decision or was seen in a run, and none is fixed in code.

## Where it looks

- **A folder outside git that holds projects.** Started in such a folder, the gate finds no repository and no test command, so it lets every turn end with one line.
- **Outside git in general.** Nothing tells what changed, so the tests run on every stop. Only Python test files in the folder itself, not in its subfolders, make it a Python project.
- **Worktrees.** Only a tree that is the agent's working folder at a prompt or a stop is watched. A worktree edited only by absolute path is not checked. A worktree moved with `git worktree move` or by hand is not followed either, so its changes from before or after the move are not seen.
- **Removed worktrees.** The gate tests the commit a removed worktree left, found through the branch the worktree had when the gate last saw it. It misses commits that end up elsewhere: on a renamed branch, on a new branch while the old one is reset back, or in a worktree switched back to its start commit instead of removed. A branch merged with `git merge -s ours` counts as merged.
- **The temporary checkout has no ignored files.** A removed worktree's commit is tested in a fresh checkout without `node_modules`, a virtual environment or a `.env`. A test command that needs them reads as did not run.
- **A removed worktree's commit is tested whatever it changed.** A commit that only edits documentation is still blocked when the tests were already failing on its branch.
- **Branches left behind.** Commits the agent makes on a branch and then leaves are not tested, for example when it switches the project back to its old branch. The gate tests what is checked out, plus the commit of a removed worktree.
- **Submodules and nested repositories.** Changes inside them are not seen: git reports the folder, not its files.
- **Files git does not report.** Changes to these are not seen: an ignored `.env` the tests read, a project inside an ignored folder, files marked `assume-unchanged` or `skip-worktree`.
- **Symlinks and permissions.** Editing a file through a symlink that points outside the repository is not seen, and neither is a change to a file's permissions only.
- **Throwing work away.** Resetting a worktree the agent entered during the turn back to a commit that existed before the turn counts as no change.
- **Report files.** The test run may rewrite a file git does not ignore (for example `junit.xml`). Then a turn that only ran the tests looks like a code change.
- **A session started in a subfolder.** The gate reads `.greenwashing.json` from that subfolder, while changes count in the whole repository.

## What it counts

- **`node --test` and `process.exit`.** A test file with no tests reads as one passing test. So does a file whose code under test calls `process.exit(0)`, and on Node 22 and 24 a file whose tests `--test-name-pattern` all leave out (seen in runs: a test script narrowed to a name no test has passes the gate on Node 22 and 24, one passing test per file on 22.22.2, 22.23.3 and 24.21.0; on Node 20 and 21 it is zero tests, GW-08).
- **`pytest.exit`.** `pytest.exit(..., returncode=0)` reads as passed.
- **Fewer tests.** A new `.only` or skip in a test file is red (GW-17), and so is a test the turn removes (see Removed tests below), but an agent can still narrow the test script, exclude files in the runner's config (jest `testPathIgnorePatterns`, pytest `-k` or `collect_ignore`), or remove a row of a test table. The gate then gets green counts for the tests that still run.
- **Skips on CI that are not seen as such.** The gate runs the tests with `CI=true`. A new test in a suite whose condition reads `CI` is red (GW-17), but a test skipped in CI some other way counts as skipped, not failed. Seen in runs: a name bound by a destructuring with a new name (`const { CI: onCi } = process.env`), by a later assignment or a function (`let onCi; onCi = ...`, `function onCi()`), imported from another file or a package (`is-ci`, `ci-info`), through more than one name, a Python name with a type annotation or in a tuple (`IS_CI: bool = ...`), and conditions on other variables, the gate's own too (`GITHUB_ACTIONS`, `CLAUDE_PROJECT_DIR`, `CLAUDECODE`).
- **Skips on CI that are reported although they run.** Any condition that reads `CI` counts, also one under which the suite runs in the gate (`describe.runIf(process.env.CI)`, `skipIf(!process.env.CI)`), and the word `CI` anywhere in the condition (`mode === 'CI'`).
- **Summary-like output.** A test that prints a line looking like a runner summary adds counts.
- **vitest `Tests  no tests`.** The result is right (did not run), but the reason is "no test counts" instead of GW-08.

## Which command it runs

- **Other runners.** Only pytest, unittest, jest, vitest and `node --test` output is read. A project whose test command, when the work starts, is none of them - no test command at all, or a test script of `package.json` that names none of them (`mocha`, `go test`, `make test`, `sh run-tests.sh`, `node scripts/test.js`, `react-scripts test`, `python manage.py test`) - is not checked: each turn ends with a line that says so, and a human who sets `testCommand` in `.greenwashing.json` makes it checked (a command a human sets there is always run; output with no counts is did not run). Only the text of the script is read, and the scripts it runs through `npm`, `yarn` or `pnpm`: a script that names a runner without running it (`eslint --plugin jest .`) counts as checked, a runner started from a file the script runs does not, flags between `run` and the script's name (`npm run --silent unit`) hide the script, and `pretest`/`posttest` are not read.
- **Checked or not is decided at the start.** The project's files at the session's first prompt decide it. A project the gate checks stays checked for the rest of the session: a test script the agent changes, even in a turn the gate accepted, does not turn it off, so a human who removes the tests and the test command between turns gets did not run until they set `testCommand` or start a new session. A project the gate does not check is decided again after each turn the gate let end, so a turn that adds the first tests is not checked and the next one is. A human's change to `.greenwashing.json` between turns decides it again at once. A `.greenwashing.json` changed during a turn still blocks in a project that is not checked (GW-114). With no prompt recorded (the hooks added in the middle of a session), a project with no test command is blocked as did not run, not passed as not checked.
- **pnpm.** `pnpm -r test` puts the package name in front of each line, which hides the counts.
- **A virtual environment not on PATH.** `python3 -m pytest` runs the system Python; set `testCommand` to the environment's Python.
- **Other Python test names.** Only `test_*.py` and `*_test.py` files, or pytest settings, make a project Python. Tests kept only in files like `tests.py` or `testing.py` need a `testCommand`.
- **Python tests without pytest settings.** They run under `python3 -m unittest discover`. That runs only `unittest.TestCase` tests in `test*.py` files; pytest-style test functions and `*_test.py` files are left out. Set `testCommand`.
- **jest and `CI=true`.** jest fails a new snapshot instead of writing it, and an explicit `jest --watchAll` still waits for the timeout.

## The quick checks of changed tests

Before the tests, the gate reads the test lines the turn added or changed. These are the limits of that reading.

- **What the checks look for.** Only a new skip, focus or expected-failure marker and a removed test (GW-17), a new or changed test with no assertion (GW-18) and a check whose two sides are the same (GW-01). The most common ways to buy green are none of these, and the tests then pass: changing the expected value to what the code returns (GW-41), deleting a table row, weakening an assertion (`.toBe(6)` to `.toBeDefined()`), swallowing the failure (`try`/`catch`, an early `return` on CI), taking the expected value from the code under test, mocking the code under test, or writing the wrong output into a snapshot. Tests that agree with a wrong change pass too: a fixture without the case that shows the bug (an error rate over requests with no health checks among them), stubs on both sides of a seam that agree with each other, a fix to one of two places with the same bug. `bench/RESULTS.md` measures these.
- **Which files are tests.** Only what jest, vitest and `node --test` collect by default (`*.test.*`, `*.spec.*`, `*-test.*`, `*_test.*`, `test-*`, `test.js`, files under `__tests__/` or `test/`) and Python `test*.py` (so also `tests.py`) and `*_test.py`. Tests under `tests/` with a jest config that points there, Cypress `*.cy.js`, Jasmine `spec/` files, `conftest.py` and runner config are not read.
- **Skips it does not see.** A skip condition changed away from its marker (`HAS_TZ = False` behind an old `skipif(not HAS_TZ)`), node:test options passed in a variable (`test('x', flaky, fn)`), a name given to a marker in another file, by a function (`function itIf(c) { return c ? it : it.skip; }`, a pytest mark returned by a `def`) or by a later assignment (`let maybe = it; if (!db) maybe = it.skip;`), a vitest `test.extend` object under another name, a skip added in `conftest.py` or runner config, a test renamed so the runner no longer collects it (`_test_...`, `test_x.__test__ = False`), a test wrapped in a string, a failing test replaced by `it.todo` with its name, and skip decorators outside pytest and unittest (Django's `skipUnlessDBFeature`).
- **Suites that skip.** A test added to or moved into a suite that never runs (`describe.skip`, `xdescribe`, a class or module marked `pytest.mark.skip`, `unittest.skip` or xfail, also through a class's own `pytestmark`) or that a condition reading `CI` skips (`describe.skipIf(process.env.CI)`, `pytest.mark.skipif(os.getenv("CI"), ...)`, also through one name the file binds to such a read) is reported, also when the suite's bracket or indentation moves around it; an edit of a test that was already there is not. A test is told by its name, so one renamed while the suite moves around it is not seen. Not seen either: a test moved into a suite that another condition skips (a platform or a version: a new honest test there must not block while the condition lets it run), into a suite skipped through a named variable, node:test suite options, a `setUp` that calls `skipTest`, Playwright's `test.describe.skip`, or a class that already has `__test__ = False`.
- **A helper that asserts under another name.** A test that checks only through its own helper (`checkUser(u)`, `verify(response)`, nock's `scope.done()`) or only by calling code that throws (Testing Library `getBy...`, a "does not throw" test) reads as "no assertion". Calls named `assert...` or `expect...`, the test's context (`t.` or its first parameter, other than members that check nothing like `t.diagnostic`) and functions imported from assertion modules (`node:assert`, `chai`) count. Otherwise turn the check off: `"checks": {"assertions": false}` in `.greenwashing.json`.
- **A test function defined elsewhere.** `test('saves', savesTheUser)` is not read; only an inline function is.
- **Assertions that cannot fail.** `assert True`, `assert.ok(true)`, `expect(1).toBeDefined()`, an assert on a non-empty tuple (`assert (x == 6, "message")`) and `console.assert` count as no assertion. Other constant checks still count as one (`expect(null).toBeNull()`, `self.assertIsNone(None)`, `expect(r === r).toBe(true)`).
- **Same sides, by text.** GW-01 compares the text of both sides (JavaScript without spaces and comments, Python by its syntax tree). Two different expressions that always hold the same value are not seen, and the same call or value on both sides is reported also where it is meant: a determinism check (`expect(f()).toBe(f())`), an identity or cache check (`assert get_config() is get_config()`), a reflexivity check (`assertEqual(cart, cart)`).
- **Lines are compared as text.** Re-indenting (wrapping tests in a `describe` or a class), a new quote style, or any edit of a line that holds an old marker (a new reason for `@pytest.mark.skip`) reports that marker again. Indentation is kept on purpose: in Python, indenting a test into a skipped class is a new skip. Past 2000 inserted and removed lines in one file, every line between the first and the last change counts as changed, so a codemod over a big file reports its old markers again.
- **Moved test files.** A new test file that keeps, in order, at least half of its lines from a test file the turn deleted is read against that file, and so is each part of a deleted file split in several. A copy (the file it came from is still there) or a file moved with most of its lines changed is new: every line counts, so an old skip in it is reported.
- **Removed tests.** A test the start of the turn had in a changed test file is removed when neither its name is still in its file nor its body is in a test file now. So a test renamed and edited at once is removed (a function and its test renamed together, when the body calls the function), while a test replaced by another under the same name counts as edited. A test moved to another test file keeps its place only where every runner of the project that collected its old file collects the new one too, by the runners' default file names (a `node --test` project's test moved to `a.spec.js`, or a unittest project's to `a_test.py`, is removed); a test file moved with at least half of its lines kept keeps its tests' names. Runner settings are not read, so a move into a file that the default names cover but the project's own settings (jest `testMatch`, a `node --test` glob, pytest `python_files`) leave out is not seen, and a move the settings allow but the default names do not (a `.js` test moved into `.ts`) is reported. The checks read tests from the text, not from what runs: a test defined under a condition (`if (process.env.X) test(...)`) or in a class unittest does not collect (`class TestX(object):` under unittest) still counts as a test. Only tests the checks see count: a test whose function is defined elsewhere (`test('x', saves)`) keeps its place by name only, and tests made in a loop, imported from another file or in a test file with no test the checks see (so that file can be deleted unseen) are not counted. Tests are compared within each tree and only among changed test files: a test moved from a worktree to the project is removed in one and new in the other, and deleting one of two copies is reported when the other copy's file did not change. A test file over 1 MiB that was dirty when the work started, or that the user changed between turns, has no known tests, so removals from it are not seen; a start text the checks' Python cannot read has no tests either (a deleted file in syntax newer than that Python).
- **Allowing a removal.** The words "allow test removal" anywhere in the user's prompt, in any case, let that turn remove any test, not only the one meant, until the turn ends; they also count inside "do not allow test removal", and in a prompt that pastes the gate's own message, which quotes them. Nothing else lets it: the agent's text and the files do not. `"checks": {"skips": false}` turns the check off together with the check of new skips. A test file the user changes after a turn the gate let end as WORK NOT ACCEPTED is theirs as it is at the next prompt: a test the agent had removed from it no longer counts. After a turn the gate only blocked, or one cut off before its stop (interrupted, or its hook killed), the agent may have changed the file after the gate last saw it, so the change counts as the agent's, and a test the user removed then needs the words too.
- **Not a parser.** The JavaScript and TypeScript reading is a scanner for strings, comments, templates and regular expressions. Unusual code (JSX text with a quote in it, a backtick in JSX text with a template later, `/*` in JSX text with a real `*/` later, a regular expression right after `)`) can make it misread a line.
- **Look-alikes.** A new doc comment with a usage example (` * it('adds', ...)`) reads as a test in a comment, and `this.skip(n)` on any object reads as mocha's skip.
- **Python.** The Python checks run `python3` from PATH, or the Python that `"python"` in `.greenwashing.json` names (a path from the project folder, or a name on PATH), which must read the project's syntax. That Python is run as it is: one the agent can rewrite (in an ignored `.venv`) decides what the Python checks report. No such Python, or a file it cannot read (syntax newer than that Python, such as `def first[T]()` under Python 3.11), is did not run on every turn until a human sets `"python"` or turns the checks off; the block says how. `"python"` is for the checks only: the test command decides which Python runs the tests.
- **No start of the turn.** Outside git, or when the prompt hook did not record the start of the turn (it failed, or the hooks were added in the middle of a session), nothing tells which lines changed: the tests run, the checks do not, and the allow line says so.
- **Big or linked files.** A test file over 1 MiB that was dirty when the turn started counts as all new. A test file that is a symlink is not read.
- **The gate's settings.** The checks and the test command of every tree, worktrees and a removed worktree's commit included, come from the project folder's `.greenwashing.json` as it was when the turn started; a worktree's own is ignored, and the gate's message says so when it differs. A change to any `.greenwashing.json` in a checked tree during the turn blocks (GW-114), also when the user made it while the agent worked. The user changes it between turns, before the next prompt; after a turn the gate did not accept, the file must then differ from what the gate last saw (see below). The project's own file counts also when git ignores it; an ignored one in another worktree changes nothing and is not seen.
- **After WORK NOT ACCEPTED.** Three blocks in a row let the agent stop. The next turn is measured from the last state the gate accepted (green tests, or no code changed), so the work and the findings it did not accept block again, turn after turn, until the tests pass, the user undoes the work, or a human turns a check off. A change the user makes between such turns (a skip of their own) counts as the agent's too. The settings are measured from the start of each turn, with one rule: each `.greenwashing.json` that differs from the turn before's settings and is still as the gate last saw it (at the last stop, or at the prompt of a turn cut off before its stop) is the agent's change carried over, so it keeps blocking (GW-114) and the tests keep the settings the work started with; a file changed since is the user's, and each file is judged alone. So a user who wants to keep a settings change made during the turn edits the file again between turns (any edit), a settings change the agent made in a turn cut off before its stop is taken as the user's, and so is one in a worktree the agent entered during the turn (no earlier settings are known there).

## Time, turns and sessions

- **`timeoutSeconds` is one budget per stop.** It bounds all test runs of one stop together: the project, its worktrees, a removed worktree's commit. With several long suites, raise it.
- **Many changed files.** Change detection reads each changed file with a separate git call, so tens of thousands of files take minutes.
- **An interrupted turn.** A turn cut off before its stop keeps its start, like a turn the gate did not accept. An edit the user makes before the next prompt then counts as the turn's change, a removed test included (see Allowing a removal); only `.greenwashing.json` is measured from the next prompt, unless it is an unaccepted change still as the gate last saw it (see After WORK NOT ACCEPTED).
- **A new session.** The gate keeps its state per session. A new session starts from what it finds, so work an earlier session left unaccepted is then its start and no longer reported.
- **Two sessions in one checkout.** Each sees the other's changes as its own, so a session that changed nothing can be blocked.
- **Someone else's work in a worktree.** The agent may only visit a worktree that holds failing work it did not make: uncommitted work of the user or of another session, or a commit fetched after the turn started. The gate tests that work and blocks. A commit the user makes in a worktree the agent was in counts as the agent's.

## The gate itself

- **Its own files.** The gate runs its code from the working tree: an agent that edits `gate/` during the turn changes what runs. A `.greenwashing.json` edited during the turn blocks (GW-114) and takes effect only from the next prompt.
- **Its state.** The state file lives in the user's temp folder, where the agent can edit it. If the gate cannot write its state folder, every stop fails (exit 2) until Claude Code's own limit of blocks.
- **Another user's folder.** On a shared machine, another user can create `greenwashing-gate-<uid>` first, open to everyone, and rewrite the state.
- **Signals.** A signal to the hook ends it with a non-blocking error, and the turn ends ungated. An example is a `pkill` the agent started. A hook killed with SIGKILL during a temporary checkout leaves that checkout in the temp folder and in `git worktree list`; remove it with `git worktree remove`.
- **A gate that cannot start.** With no `node` on PATH, or a moved `gate/hook.js`, Claude Code treats each hook's error as non-blocking: every prompt and stop shows its own "hook error" notice (seen in a run: "/bin/sh: 1: node: not found") and the turn goes on unchecked. The gate's session hook says at the start of each session that the gate is off and that Node.js 20 or newer is needed; the shell prints that line, so it is written for `sh` (Git Bash on Windows) and is not tried in PowerShell, which Claude Code uses on Windows without Git Bash. A Node too old to load the gate at all gives the same notices (seen in runs: 14.17.6 cannot load it, 14.21.3 and 16.20.2 get the gate's own line).
- **An older Node.** The gate needs Node.js 20 or newer, the oldest one CI tests (Node 18 ran a simple project in a run, but CI does not test it). On an older Node it does not run: the session start and each stop say so, and the turn is never blocked for it. The mutation command does not check the Node version.
- **Documentation by extension.** A turn that changes only `.md .markdown .rst .adoc` files skips the tests, even when tests read those files. In this repository that is true of `CATALOG.md` and `SKILL.md`.
- **The block message.** It names up to 10 failed tests, read from TAP, pytest, jest, vitest and unittest output, and shows the last 20 lines. Other output gives no names: the `spec` reporter of `node --test` (its default on Node 23 and later, also when the output is not a terminal) and other runners.

## The mutation command

The command breaks the code lines a change added, one break at a time, in a temporary copy of the working tree, and runs the project's tests after each break. These are the limits of what it tries and of what its outcomes mean.

- **What it breaks.** Only JavaScript, TypeScript and Python lines added or changed since the merge base with the main branch (`origin/HEAD`, else `origin/main`, `origin/master`, `main`, `master`; `--base` sets another), committed or not, and untracked files, in the project's folder. Test files, files in `test`, `tests`, `__tests__`, `__mocks__`, `spec`, `e2e` and `cypress` folders (production code kept in such a folder too), `conftest.py`, `*.config.js`, test setup files (`setupTests.js`, `*.setup.js`), `.eslintrc.js`, `*.cy.js`, `*.test-d.ts` and type declarations (`*.d.ts`) are never broken. A break in a TypeScript type (`type Port = 8080`) changes nothing at run time and always survives. Six kinds only: a comparison turned around, an `if` condition negated, a guard (an `if` with one `throw`, `raise` or `return` and no `else`) removed, a returned value replaced by `null` or `None`, `true` and `false` swapped, a number one higher. A bug of another kind is not tried: a defect with no break of these kinds at its place (a `reverse=True` left out, where a one-item test cannot see the order) survives no break, and neither does a defect in lines the change did not touch (the second call site of a half fix).
- **How it reads JavaScript.** With the scanner of the quick checks, not a parser. A comparison is broken only between a name, a number or a bracket and an operand, with spaces on the same line (`a < b`, not `a<b`), so TypeScript generics and JSX tags are left alone; a number in JSX text is broken like code. A guard is removed only when its lines hold nothing else, a comment included. A `.js` or `.cjs` break that no longer compiles is dropped; other files are not checked that way. Checked on installed packages: all 53,589 breaks of 1,059 CommonJS files and a sample of 12,184 of 859 ES modules parse with node's parser, all 5,186 breaks of 211 TypeScript files with TypeScript's.
- **A sample.** At most 20 breaks (the limit). Every file gets a break before any gets a second, and in each file every kind before any gets a second, spread over the file. A big change gets a sample, not every break.
- **Survived is not always a missing test.** A break can leave the code doing the same thing (an equivalent break, such as a number that only names a size). Each survivor needs a look: a missing test, or a reason why the break changes nothing.
- **Did not run.** A break the tests did not finish on (for example one that makes the code loop forever), a run with no counts, zero tests or a file that could not run is did not run, never caught. Under `node --test` a break that makes a test file fail to load is reported by the runner as a failed test, so it counts as killed.
- **One control run.** The tests run once on the unchanged copy and must be green. A flaky test that fails during one break's run makes that break look killed.
- **Control breaks.** Before the breaks, each file with a break in the sample is made to fail as soon as it runs (a function that throws, called at once, or a `raise` after the docstring and the `__future__` imports). When the tests still pass, they do not run that file: its breaks are not exercised and count as did not run. Only green says that; any other outcome (failed tests, a file that could not load, no counts) counts as the tests running the file, also when a flaky test failed during that run. A file loaded inside a `try` that catches every error and falls back to other code (an optional fast module) reads as not exercised: the fallback runs and the tests pass. A control break the tests do not finish on leaves its file's breaks as did not run. Files with no break in the sample get no control break. The control runs share the limits for time, not the limit of breaks.
- **The copy holds what git lists.** Tracked files as they are in the working tree, and untracked files git does not ignore. Ignored files (`.env`, build output, generated code) are not in it, and it is not a git checkout: tests that need them do not pass the control run, so everything is did not run.
- **Linked dependencies.** `.venv`, `venv`, submodules and nested repositories are linked into the copy, not copied; `node_modules` is a folder of the copy's own with a link to each entry of the user's. The caches tools write there (`.cache`, `.vite`, `.vitest`) stay in the copy, and a workspace package linked into it points to the copy's files. Other writes into a linked folder (inside a package, into `.venv`) reach the user's. Code the tests import through a link out of the copy is the user's file, not the copy's: its breaks do not reach the tests. That is the case for an editable install of the project in the virtual environment, a built copy the tests load instead of the source, or a path outside the copy: the control break shows it, and the file's breaks are not exercised (seen in a run: a src layout with `pip install -e .`, pip 24.0).
- **Outside the copy.** The tests of each break run as the user. A test that writes to an absolute path, a shared temp folder or a database is not kept inside the copy.
- **Time.** The limits are 10 minutes for everything and 120 s for one run. A suite slower than that is did not run until the limits are raised (`"mutants"` in `.greenwashing.json`, or `--timeout` and `--run-timeout`).
- **Signals.** SIGTERM, SIGINT, SIGHUP and SIGQUIT stop the tests and remove the copy; files the stopped tests made outside it (their own temp folders) stay. A command killed with SIGKILL leaves its copy in the temp folder (`greenwashing-mutants-*`) and the tests running; remove it by hand. A copy that cannot be removed is said, and is did not run.
- **Tests that read the code's text.** A test that checks the source itself (a hash of the file, a snapshot of its text) fails for every break, so every break counts as killed.
- **Which tree.** The command reads the tree of the folder it is given (`--project`; the plugin command gives the project folder) and that folder's `.greenwashing.json`. Changes in another worktree are not seen; run it with `--project` at the same place in that worktree.
- **The Python that lists the breaks.** It is `python3` or the `"python"` setting, run as it is. Its breaks are tried only when they are of a known kind on a changed line, but one the agent can rewrite can still leave breaks out.
- **Python breaks.** Read with Python's `ast`, from `python3` or the `"python"` setting. Code inside f-strings is not broken, an `elif` is never removed as a guard, and a file that Python cannot read is did not run.
